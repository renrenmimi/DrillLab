# 引导计划 · 架构与实测

上一轮把导航改成了「意图优先」（[intent-nav.md](intent-nav.md)）：顶栏四个模式回答
「我现在想做哪一类事」，侧栏回答「在这件事里我在哪」。那一步是对的，但它只解决了一半。

## 一、剩下的那一半

**四个模式里只有 Learn 是线性的。** Review / Practice / Assess 仍然是题库、筛选器和列表。
于是下面这些话在站里得不到一条完整的路：

| 用户说的 | 上一版给他的 |
| --- | --- |
| 「我要准备 React 考试。」 | 105 道题的题库、一堆筛选器、7 道考场题 |
| 「我要学 GraphQL Federation。」 | 一门 17 节的课，和三张不知道什么时候该来的全量表 |
| 「我要准备 Spring Boot 那道控制器题。」 | 无 —— 那道题的材料散在一门课的第 4 部分、一道 coding、一道考场题里 |
| 「我要复习前端面试。」 | 8 个方向的筛选按钮 |
| 「我要把 Cab Booking 重做一遍。」 | 一门 8 节的课 + 一道 coding + 一道考场题，三处入口 |
| 「我从零开始。」 | 「从地基第一节开始」，然后呢？ |

每一句都是一个**目标**，不是一类活动。所以这一轮加的不是第三套导航，是在四个模式**之上**
加一层「把目标翻译成有序步骤」的东西。

两个入口互补，不是替代：

```
引导计划   「告诉我下一步做什么」   /plans
四个模式   「让我自己挑」          /path  /drill  /practice  /arena
```

进度是同一份 —— 见第三节。

## 二、六条计划，以及它们引用了什么

计划定义在 [content/plans.ts](../content/plans.ts)。每一档不是内容拷贝，是一个**查询**：
`{ from: "lessons", examId: "react" }`、`{ from: "drills", tracks: ["react"] }`、
`{ from: "coding", ids: [...] }`。标题、时长、题面全部从 `content/nav.ts` 现取。

| 计划 | 档 | 条目 | 映射（全部核对过真实 id） |
| --- | --- | --- | --- |
| 从零完整学习 | 20 | 350 | 四门课各自的 课文 → 练习 → coding → 考场 → 模拟考，最后 105 道八股 + 15 道手写/组件题 |
| React 考试准备 | 7 | 130 | 地基 9 节 → React 21 节 → react 方向 36 道八股 → 54 个练习 → 7 道 React coding → 2 道从零重写 → 模拟考 A |
| GraphQL Federation 考试准备 | 7 | 90 | 地基 9 节 → Federation 17 节 → node/db/web 共 12 道八股 → 47 个练习 → orders-subgraph + spring-endpoints → 2 道从零重写 → 模拟考 B |
| Spring Boot 控制器准备 | 4 | 12 | `g-spring-basics` + `g-endpoints` 两节 → 那两节的 7 个练习 + `g-lab-java-500` → `spring-endpoints` → `g-rebuild-controller` |
| 前端面试复习 | 8 | 234 | 八股按方向分四档（HTML+CSS 13 / JS+TS 44 / React 36 / Node+DB+Web 12）→ 8 节讲解 → 16 个练习 → 8 道手写题 → 7 道组件题 |
| Cab Booking 完整练习 | 6 | 38 | 地基 9 节 + React 5 节（组件/props/state/useEffect/Context）→ Cab Booking 8 节 → 15 个练习 → `cab-booking-app` → `cb-from-scratch` |

**没有内容就整档不出现。** Spring Boot 那条只有 4 档：题库里没有 Java/Spring 方向的八股，
所以没有「背」那一档；Federation 也没有对应 Java 的模拟考，所以那条计划里也没有。
不塞充数的东西。

几处需要说明的判断：

- **前置那一档来自内容自己**。`exam.prerequisites` 里写着 react / federation / cab-booking
  都依赖 foundations，所以「前置」不是我挑的，是数据里本来就有的关系。
- **Federation 的「背」那一档用 node / db / web**。题库里没有 GraphQL 这个方向 ——
  这一档在页面上明写了为什么：那 12 道正好是 subgraph 和 Spring 服务会被追问的东西。
- **Cab Booking 多了一档「React 的这几节」**。这一档是人挑的（5 节），页面上也明写了理由：
  这道题只用到 React 里的五样东西，不必把整门 React 走完。
- **前端面试复习不含 Learn 整门课**。interview 那门课的前 15 节课文**就是**八股答案
  （`content/drills.ts` 从它派生），所以再列一遍 Learn 是同一份内容读两次。
  只有 `iv-coding` / `iv-hand` 那 8 节是真讲解，它们进了 Learn 那一档。

### 摊开方式按内容类型选，不只看条数

课文 21 节也是一行一个 —— 那是一条课程路线，每一节有名字、有估时、值得单独点进去。
练习 54 个、八股 36 道才用格子（`autoLayout()`：只有 `exercises` 和 `drills` 且超过 14 条）。
格子上**没做的显示编号、做完的显示对勾**，真实标题挂在 `aria-label` 和 `title` 上，
而且那一档上面永远单独给一行带标题的「下一格」。

## 三、进度：一份数据，两个视图

`localStorage` 的键仍然是 `drilllab-progress-v1`，**没有升 v2**。只加了三个字段：

```ts
plan?: { id: string; startedAt: number; at: number };
planSeen?: string;      // 最近看过哪条计划的详情页
planOptOut?: boolean;   // 用户说了「先自己逛」
```

计划里每一格的完成状态**全部推导**（[lib/plan-progress.ts](../lib/plan-progress.ts)）：

| 计划里的一格 | 读的是 |
| --- | --- |
| 课文 | `lessons[`${examId}/${lessonId}`]` |
| 练习 | `exercises[...]`，从零重写那一类读 `rebuilds[...]` |
| 八股 | `drills[id]` 有记录 = 过过一遍；`mark === "known"` = 会了 |
| coding | `coding[id]` |
| 考场 | `arena[id]` 里有 `outcome === "passed"` 的那一次 |
| 模拟考 | `mocks[`${examId}/${mockId}`]` |

**为什么必须推导。** 一个人可能先自己刷了三十道八股，几天后才选「前端面试复习」。
如果计划自己记一套完成度，那三十道就白刷了 —— 他会看到 0 / 105。反过来，跟着计划
做完一节课，回到 Learn 模式那一节也必须是打过勾的。实测：造一份**不含 plan 字段**的
老数据（3 节课 / 2 个练习 / 1 套模拟考 / 1 次考场通过 / 1 道八股 / 1 道 coding），
打开 `/plans/react-assessment` 完成度直接是 12 / 130，不是 0。

### 八股这一档的口径

- **自评过一次就算过了这一档** —— 不逼人把每道都标成「会」才让走下一档。
- 「会了」的条数**单独显示**（`stat.confident`），和「过过一遍」分开。
- 推荐下一道时按 没见过 → 不会 → 模糊 → 会 排。所以一档做完之后，它仍然能给出
  「最不熟的那一道」（`weakestDrill`），计划走完的页面上就用它。

### 考场这一档

四种状态各有自己的字和形状：没试过 / 正在计时 / 试过没通过 / 通过了。
**通过才算这一档完成**，但从来不锁 —— 未来的档全都点得开。

### 「下一格」只有一个算法

```
① 计划顺序里第一个没完成的档
② 那一档定义顺序里第一个没完成的格（八股按上面那个优先级）
③ 全部完成 → 计划完成态
```

页面上任何地方要「下一步」都读这一条（`PlanStatus.next`）。顶栏那颗 Continue、
侧栏面板、计划页头、路线图里那一格高亮、课尾那一步，五处同一个来源 ——
上一轮 IA 审计记的「同一个问题在一屏里两个答案」不能再犯。

## 四、性能：懒加载是硬要求，不是优化

算完成度要展开计划，展开计划要读 `content/nav.ts`（120 KB 原始字节）。
第一版把计划零件直接 import 进外壳（`app-shell` 在根 layout 里），结果**每一个路由**
都开始下载 nav：

| 路由 | main | 第一版 |
| --- | --- | --- |
| `/drill/[id]` | 373 kB | 525 kB |
| `/code/[id]` | 387 kB | 539 kB |
| 课程页 | 470 kB | 625 kB |

而这些零件有一个共同点：**没跟计划的人身上它们一个字都不渲染**（每个都以
`if (!ready || !status) return null` 开头），而 `ready` 只有 hydration 之后才为真。
所以那 160 KB 是白下的。

现在的结构（[components/plan-slots.tsx](../components/plan-slots.tsx)）：

- 插槽文件本身不 import 任何内容模块，只有 `Link`、`useProgress`、一个内联 SVG；
- 先用 `useProgress()` 看一眼「有没有在跟计划」（`progress.tsx` 本来就在外壳里）；
- 真的在跟，才 `next/dynamic` 把 `plan-kit` 拉进来。
- 顶栏那个「计划」入口是静态的 —— 它必须在首屏 HTML 里，否则四个模式会在
  hydration 之后横向跳一下。

另外两处同样的处理：

- **`components/continue.tsx` 不许碰计划。** 它在外壳里，每个路由都下载它。
  跟着计划走时，顶栏那颗按钮换成懒加载的 `PlanContinueButton`。
- **课尾那一步拆成轻壳 + 懒加载真身。** 默认那句「接着看下一节」是首屏可见内容，
  必须服务端渲染；计划版本（`LessonPlanStepLive`）住在 `plan-kit` 里 ——
  放在单独文件会让 webpack 把 `plan-kit` 提成初始 chunk（实测过）。
  两份同时渲染，计划那份到位时用一条 CSS 把默认那份收起来
  （`display: none` 的元素不参与 `counter-increment`，所以编号不跳号）。
- **练习清单从 nav.ts 搬到 [content/nav-exercises.ts](../content/nav-exercises.ts)。**
  计划要那 148 个练习 id，但 nav.ts 每页都下载。合在一起时 nav 从 133 KB 长到 160 KB，
  webpack 分块随之改变，课程页多下 145 kB。分开之后 nav.ts 和 main 基本一致。

### 实测结果

客户端真正要下载的**总原始字节**（去重后，`app-build-manifest` 逐路由累加）：

| 路由 | main | 本分支 | 差 |
| --- | --- | --- | --- |
| `/` | 465 | 543 | **+78** |
| `/plans` | — | 525 | 新 |
| `/plans/[planId]` | — | 529 | 新 |
| 课程页 | 470 | 635 | **+165** |
| `/drill` | 469 | 475 | +6 |
| `/drill/[id]` | 373 | 379 | +6 |
| `/code` | 375 | 381 | +6 |
| `/code/[id]` | 387 | 390 | **+3**（Sandpack 仍然没进首屏） |
| `/practice` | 561 | 567 | +6 |
| `/arena` | 461 | 467 | +6 |
| `/path` | 460 | 465 | +5 |
| `/mock/[examId]/[mockId]` | 377 | 383 | +6 |
| `/guide` | 351 | 351 | 0 |
| `/reference` | 407 | 407 | 0 |

`next build` 报的 First Load JS：`/` 146 → 170 kB，课程页 141 → 195 kB，
其余 +1 ~ +3 kB，`/plans` 164 kB、`/plans/[planId]` 165 kB。

**两处还没压下去，如实记下来：**

1. **首页 +78 kB。** 首页现在就是那张「你想达成什么目标」的选择表，六张卡要算六条
   计划的完成度 —— 这一份是首屏内容，压不掉。
2. **课程页 +165 kB。** 这一处是 webpack 的分块决定，不是代码里多 import 了什么：
   把 `lesson-body` 里所有计划相关的代码**全部删掉**重新构建，课程页仍然是 631 kB
   （实测）。同一个外壳在 `/drill/[id]` 上只 +6 kB。原因是课程页的客户端模块本来就多，
   webpack 把那个共享的异步 plan chunk 提成了它的初始 chunk。
   **下一步怎么修**：让 plan chunk 不再引用 `content/nav` —— 在 `gen:nav` 里多生成一份
   自包含的 plan 索引（去重之后约 367 条，40 KB 上下），`plan-kit` 只读那一份。
   那样即便再被提成初始 chunk，代价也只有 10 kB 上下。这一步没做进这个 PR，
   因为它要动生成器和解析器，风险不该和导航改动混在一起。

## 五、完整性断言

`content/plans.ts` 的引用写错就**构建失败**，不是页面上安静地少一格。
断言在 [content/plans-assert.ts](../content/plans-assert.ts)，由 `/plans` 和
`/plans/[planId]` 两个预渲染页面 import，所以 `next build` 一定跑到它。

会抛的情况：

- 引用了不存在的课程 / 模块 / 课文 / 练习 / coding 题 / 考场题 / 模拟考
- 引用了不存在的八股方向
- 一条计划零档
- 某一档解析出 **0 条**（查询写错了 —— 真没内容就该整档删掉）
- 某一档没写「为什么在这儿」
- 同一条计划里同一个条目出现两次（会重复显示，而且完成度分母虚高）
- 计划 id 或档 id 重复

**为什么不放在 `content/plans.ts` 的模块作用域**：断言要把六条计划全部展开一遍，
而顶栏那枚计划徽标在每一页都有 —— 那样每个页面都会在客户端展开一千多个条目。

`rgba(255,255,255,0.055)` 之后，`--tk-com`（注释）掉到 4.45:1。行号早就单独提过一档

流程断言 **113 条全过**，覆盖 brief 里那 24 条：

1. 老进度（没有 plan 字段）读回来一条不丢，而且直接算进计划完成度
2. 第一次来能选 React 计划（点卡片上的「开始」就设为当前计划）
3. 刷新之后计划还在
4. 顶栏 Continue 指向计划的下一格，并标成「来自计划」
5. 学完一节，侧栏的下一格前进；写进的是既有的 `lessons`
6. 做完练习，那一档的完成数 +1
7. 自评八股，「过过一遍 / 会了」两个数分别更新
8. 推荐下一道优先没见过和不熟的；自评之后**不自动跳页**
9. 做完 coding，那一档变 1 / 1
10. 正在计时的那一格标成 live；run 页只给位置、不给离开的按钮
11. 通过之后「空手做」那一档算完成
12. 逛 7 个跟计划无关的页面，计划和开始时间都不变
13. 换计划 / 不跟计划，课程、八股、coding 进度一条不动
14. 全部做完 → 完成态，不再给「继续」按钮
15. 四个模式照旧；没跟计划时计划面板、位置条、课尾说法全部回到原样
16. 搜索能搜到计划、计划里的某一档（带 `#stage-` 锚点），也照旧搜到课文和题目
17–20 无控制台报错、390px 无横向溢出、深浅两套、中英两套（在扫描里）
21. 窄屏抽屉关着时整块 `inert`；抽屉里有计划面板
22. Esc 关抽屉 / 关 `?` 菜单，焦点都归还
23. 六条计划里可见的条目链接共 **765 条**，没有空链接；抽样打开 5 条都是 200
24. 原来的 252 个页面照旧，加 7 个计划页面 = 259

## 七、无障碍

- 路线图的状态**不靠颜色单独表意**：站点是「实心+对勾 / 强调色+光环 / 空心」，
  行上有「做完了 / 没做 / 通过了 / 正在计时」的文字，格子是「虚线+编号 / 实线+对勾」。
- 每个格子的 `aria-label` 是「序号. 真实标题 — 状态」，所以键盘和屏幕阅读器读到的
  是标题，不是「01」。
- 计划页的档是原生 `<details>`：零 JS，键盘和屏幕阅读器免费得到正确行为，
  当前那一档默认展开，其余点一下就开 —— **从来不锁死**。
- 进度条带 `role="progressbar"` 和 `aria-valuenow`。
- 顶栏那枚计划徽标和四个模式在**同一个 `<nav>`** 里，只渲染一份 DOM ——
  窄屏靠 `grid-area` 挪到第二行，不另渲染一份（否则无障碍树里会有两个同名地标）。
